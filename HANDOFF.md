# Handoff — nxIIoT Gateway (gateway component only)

This is the gateway (Go backend) split out of the original nxIIoT Gateway monorepo, for deployment to a maisvch MaxGate400 device. It carries over the gateway-relevant architecture decisions, bugs found via live testing, and known gaps from that project's history. Internal-server- and web-frontend-specific content has been left out — those components aren't part of this repo. For day-to-day dev commands see [README.md](README.md).

## What's implemented

| Area | What | Key packages |
|---|---|---|
| Acquisition | Modbus RTU/TCP master, data type/byte-order decode, quality classification, continuous round-robin polling per connection with block-read batching | `internal/modbus`, `internal/acquisition` (poller.go, blockplan.go) |
| Config | Connection/Device/Data Point CRUD API, live config reload (no restart), Test Connection/Read, COM port dropdown | `internal/api`, `internal/connection`, `internal/device`, `internal/datapoint`, `internal/acquisition/manager.go`, `internal/system/serial.go` |
| Queue | Every reading persisted to `data_queue`, per-gateway sequence ID, quality/priority, max-rows sweep | `internal/queue` (queue.go, maxrows.go), `internal/processor` |
| Store & Forward | Queue state machine (PENDING→SENDING→SENT/retry), exponential backoff, batching, crash recovery, storage threshold/full policy | `internal/queue` (dispatch.go, backoff.go, storagepolicy.go), `internal/forwarder` |
| Forwarding | `MQTTAdapter` (QoS 1, application-level ack over a dedicated ack topic, TLS/auth, auto-reconnect, reconnect watchdog) and `HTTPAdapter`, selected via `forwarder.transport` | `internal/forwarder` (mqttadapter.go, wire.go, adapter.go) |
| Time | Hand-rolled SNTP client, Linux hardware RTC (`/dev/rtc0` ioctls) with cross-platform fallback, SYNCED/RTC/UNSYNCED/INVALID quality | `internal/time` (package `timeservice`) |
| Diagnostics | Backend diagnostics counters, in-memory log ring buffer, config export/import | `internal/diagnostics`, `internal/logger/ringbuffer.go`, `internal/api` (configio.go, dashboard.go, diagnostics.go, logs.go) |
| Network | Storage WARNING/CRITICAL/FULL levels; host network IP config (`nmcli`-backed, confirm-or-auto-revert safety net) | `internal/queue/storagepolicy.go`, `internal/modbus/quality.go`, `internal/netconfig`, `internal/api` (settings.go, network.go) |

## Architecture decisions worth knowing before touching this code

- **Acquisition never depends on the server.** `acquisition.Manager` and `forwarder.Forwarder` are independent goroutines that only share the database. A dead MQTT broker/server should never slow or block Modbus polling — this is Rule 1 and is load-bearing for several other decisions below. Verified under a full network partition, not just a stopped downstream service.
- **`acquisition.Manager` diffs and hot-reloads.** Every connection/device/data point CRUD call triggers `Manager.Reload(ctx)`, which diffs the desired set against what's currently running and starts/stops/restarts only what changed. This is why config changes don't need a gateway restart — **except** a Settings save (Gateway/MQTT/Time), which restarts the whole process deliberately, because it's changing MQTT/Time subsystem config, not device polling config.
- **Sequence IDs are assigned atomically with the insert.** `queue.Repository.Insert` does `UPDATE gateway SET last_sequence = last_sequence + 1 ... RETURNING last_sequence` inside the same transaction as the `data_queue` INSERT. Survived a real `SIGKILL` mid-write with no gaps or resets.
- **The forwarder's transport is behind an `Adapter` interface** (`internal/forwarder/adapter.go`). `HTTPAdapter` is the dev/test transport; `MQTTAdapter` is the production one. Swapping is a one-line change in `cmd/gateway/adapter.go` driven by `forwarder.transport` in config.
- **`internal/queue` owns all `data_queue` SQL.** `internal/processor` and `internal/forwarder` call into it rather than querying the table directly.
- **Every long-running loop is a bare goroutine over the same top-level `context.Context`**, cancelled on SIGINT/SIGTERM: max-rows sweeper, storage pressure sweeper, `forwarder.Run`, `timeservice.Run`. `main.go` is the single place that wires all of them.
- **Platform-specific code is isolated behind a package-level interface, not build tags, when the underlying call is just `os/exec` or similarly portable** (`internal/netconfig`'s `nmcli` invocation) — build tags (`internal/time/rtc_linux.go` vs `rtc_other.go`) are reserved for genuinely platform-specific syscalls (`golang.org/x/sys/unix` ioctls) that literally won't compile elsewhere.
- **Config the API can write back is a full `yaml.Marshal` re-encode, not a comment-preserving patch.** Deliberate simplicity tradeoff — `config.Save` loses any hand-written comments in `config.yaml` the first time it's used.
- **A settings change that needs a process restart calls `os.Exit(0)` and relies on the process supervisor to restart it** (`deploy/nxiiot-gateway.service`'s `Restart=always`) — rather than the app trying to re-exec or restart its own subsystems in place. Keeps the restart path identical to a crash-restart, which is already tested.
- **One goroutine per physical connection, not per device.** `Poller.runConnection` owns a single `modbus.Client` for the connection's lifetime and calls `SetUnitID` before each sibling device's own reads, serialized by construction — several devices can share one RTU bus (real multi-drop) without corrupting each other's frames on the wire. This replaced an earlier flat `device` schema where each device opened its own independent serial handle, which caused real frame corruption when two devices shared a bus.
- **Datapoints are batched into as few Modbus block reads as possible per device** (`internal/acquisition/blockplan.go`), instead of one request per datapoint — groups same-function-code datapoints by contiguous/near-adjacent register ranges (capped at the 125-register PDU limit, never splitting a datapoint's own span, tolerating small gaps up to 8 registers). FC1/FC2 (coils/discrete inputs) are intentionally left ungrouped — see Known gaps below.
- **Polling is a continuous round-robin scan**, not a per-device/per-datapoint ticker — a single connection-level `next_device_delay_ms` paces between devices. The earlier two-level `polling_interval_ms` scheme (device *and* datapoint each independently gating reads) was a real, documented footgun: changing only one had no visible effect on read cadence.
- **The API router can optionally serve the built `web/` frontend on the same port as the REST API** (`api.static_dir` in config, wired in `internal/api/router.go`) — a plain `http.FileServer` mounted on `/*` after the `/api` routes, no reverse proxy, no CORS. Added for the MaxGate400 deploy (2026-09-03), where the device has no internet access and no Node runtime; the original monorepo's own deploy plan (`web/deploy/nxiiot-gateway-web.service`) runs the Vite **dev server** persistently instead, which isn't appropriate for a locked-down production device. Empty (default) disables it, so this doesn't change behavior for any other deployment of this binary. The frontend has no client-side routing (single tab-state SPA, no react-router), so no SPA-fallback logic was needed.

## Bugs found via live testing (not caught by unit tests alone)

Recurring lesson for this codebase: **unit tests run against fresh temp state; real bugs have consistently shown up only under live testing with real accumulated state, real network conditions, or a genuinely killed process.**

1. **`modbus.QualityFromError`** originally matched `"connection refused"` (Linux wording) but not Windows's `"actively refused it"` for the identical condition — only visible testing the native Windows build against a real refused connection. Fixed with explicit per-platform substring matching; regression test dials a real closed OS socket.
2. **A migration** used a non-constant `DEFAULT (strftime(...))` on `ALTER TABLE ADD COLUMN`, which SQLite only rejects on a table that already has rows — every test's fresh temp DB has zero rows, so this only surfaced against a real, populated database. Fixed with a constant epoch default.
3. **`modbus.QualityFromError`** again: a real network-partition chaos test made the embedded DNS resolver fail with `"server misbehaving"`, which matched none of the existing substring checks and fell through to `INVALID` instead of `DEVICE_OFFLINE`. Fixed with an explicit `errors.As(err, &dnsErr)` check for `*net.DNSError` (catches every DNS failure mode, not just this string).
4. **NTP Server field accepted an ntp.conf-style value with zero validation** (`internal/api/settings.go`'s `saveSettings`) — pasting `server 0.th.pool.ntp.org` (the word "server" is standard `/etc/ntp.conf` syntax) instead of the bare hostname saved successfully with no error, then failed DNS resolution at sync time and silently fell back to `RTC` quality — invisible unless you read `GET /api/time` or the logs. **Fixed**: `normalizeNTPServer` strips a leading `server `/`pool ` token and rejects embedded whitespace with a `400` instead of saving it.
5. **paho.mqtt.golang's AutoReconnect silently stalled after a "pingresp not received" disconnect** — the client logged exactly one `"mqtt connection lost, will auto-reconnect"` and then never recovered for 7+ minutes, despite the broker staying reachable the whole time. `SetAutoReconnect(true)`/`SetConnectRetry(true)` are not self-healing forever. Fixed with `MQTTAdapter.RunReconnectWatchdog` (`internal/forwarder/mqttadapter.go`) that forces a manual reconnect once the client has been stuck disconnected past a threshold well beyond paho's own retry interval.
6. **The reconnect watchdog itself had a bug** that made a later outage worse: it called `client.Disconnect(250)` unconditionally right before its own `Connect()`, tearing down paho's own legitimate in-flight reconnect attempt — paho's `"status can only transition to connecting from disconnected"` error means paho was already actively, correctly retrying, not stuck. Fixed by removing the preemptive `Disconnect()` and detecting that specific paho error as informational, not a failure requiring action.
7. **`SetMaxOpenConns(1)`** — set as a blanket "avoid SQLITE_BUSY" strategy — forced *every* DB operation (acquisition inserts, forwarder fetch/mark, retention/storage sweeps, and every API read) through one single serialized SQLite connection, even though WAL mode is specifically designed to let readers run concurrently with SQLite's own single-writer enforcement. A slow read query queued directly in front of the acquisition goroutine's own time-critical insert on that one shared connection, producing multi-second poll-duration spikes that looked like hardware/I-O contention but weren't. Raising it to 4 fixed the real bottleneck — but doing so exposed a second, more subtle bug (next item).
8. **`queue.FetchBatch()`'s SELECT-then-UPDATE-in-one-transaction pattern relies on no other writer landing in between** — true only with a single connection. The moment `SetMaxOpenConns` rose above 1, concurrent `Insert()` calls from acquisition could land mid-transaction and produce `SQLITE_BUSY_SNAPSHOT` (error 517), which `busy_timeout` does **not** retry (a stale read snapshot, not simple lock contention). Every forwarder dispatch failed continuously for ~9 minutes before catching it. Fixed with `_txlock=immediate` on the DSN so every explicit `BeginTx` takes its write lock at `BEGIN` instead of after its read, closing the window entirely.
9. **`cp` onto a running binary fails with `ETXTBSY`.** Linux refuses to open a file for writing while it's mapped as another process's executable text segment. Deploy pattern: copy to a different filename, then `mv` over the target — `rename()` doesn't need write access to the old inode.
10. **A migration file existed in the git checkout but wasn't copied into the deployed system's separate migrations directory** before restarting — the running binary immediately failed to start acquisition with a "no such column" error. Any deploy that ships a new migration needs that copy step, separate from and in addition to the binary swap.

**Takeaway for future work on this repo**: after unit tests pass, do a real end-to-end run — and for anything touching failure/recovery paths specifically, an actual chaos test (network partition, `SIGKILL`, stopping a real dependency) — before considering a change done.

## Known gaps / untested paths (be honest about these, don't assume they work)

- **RTU**: the CRC-error/`DEVICE_OFFLINE` failure paths (unplug mid-poll, forced bad response) haven't been triggered from live hardware yet on the original deployment — the classification logic itself is unit-tested against a real frame decoder (`goburrow/modbus`), just not exercised from live hardware. Datapoint polling intervals are hardware-dependent: the original deployment's sensor held `GOOD` quality down to 250ms but timed out completely below that — step down gradually on new hardware rather than jumping to an aggressive interval.
- **RTC hardware**: `internal/time/rtc_linux.go`'s `/dev/rtc0` ioctls cross-compile clean; whether real hardware is wired up depends on the specific device. On the original deployment the actual chip was an Epson RX8010SJ via an out-of-tree DKMS kernel module (`AUTOINSTALL="yes"`, so it should survive a kernel upgrade automatically, though that was never proven against a real upgrade) with the I2C device instantiated via a udev rule rather than a `dtoverlay=i2c-rtc` line — don't assume a standard overlay-based RTC install; check `dmesg | grep -i rtc` and `/dev/rtc0` directly.
- **Host network IP (`internal/netconfig`)**: `Current()` was confirmed live against a real device's `nmcli`. `ApplyStatic`/the confirm-or-auto-revert flow was still unverified as of the original deployment — deliberately deferred until physical console access is arranged, since a bad static-IP apply could lock out the only remote path to the device. **Test this last, with console access as a fallback.**
- **MQTT reconnect has failed silently in two genuinely different ways on real hardware** in the original project's history (see bugs #5 and #6 above) — treat any future "was connected, now isn't, and isn't coming back" report as a new investigation, not automatically one of these two.
- **`word_order`** is a stored-but-unused datapoint field — `byte_order` alone (e.g. `"ABCD"`/`"BADC"`) already fully specifies both byte and word order for 32/64-bit types. Documented in `internal/modbus/decode.go`.
- **FC1/FC2 (coil/discrete input) decoding is broken independent of anything recent** — `DataType.RegisterCount()`'s byte-width math (built for INT16/UINT16/INT32/UINT32/FLOAT32/FLOAT64 register values) doesn't match Modbus's bit-packed coil/discrete-input response format. Not currently blocking anything unless a coil/discrete-input datapoint is configured.
- **`modbus.ReadWithRetry` is called with `maxRetries=0` hardcoded** even though `connection.Connection.Retry` exists, is validated, and is otherwise unused.
- **`gateway.db` doesn't shrink on disk after an eviction sweep (max-rows or storage-pressure) deletes rows** — SQLite frees pages internally for reuse but doesn't return them to the OS without `VACUUM` or `auto_vacuum`. `VACUUM` needs an exclusive lock on the whole file for its duration — worth timing against real acquisition/forwarder traffic before running it on a live device, not a quick admin-button add.
- **Config save is a full-file re-marshal.** Editing `config.yaml` by hand and then saving once through the API/UI will silently discard those hand-written comments/formatting. Not a bug, but a footgun worth remembering.
